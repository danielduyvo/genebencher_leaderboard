Methods

Methodology

What is measured, how a task becomes a score, and what this dashboard deliberately does not claim.

1. What the benchmark measures

GeneBencher asks an agent to perform a complete analysis on a synthetic but biologically structured cohort: genotype QC, bulk differential expression, single-cell annotation, cis-eQTL mapping, network inference, fine mapping and functional annotation. Inputs are mounted read-only; truth is never mounted. A task is graded by a task-specific grader on the declared deliverables.

The generator is synthetic by design. It gives a known truth and controlled confounders without shipping human data. The trade-off is that absolute scores describe performance on this generator, not on every real dataset.

2. From sub-scores to a task score

Each task declares a pass threshold and a set of weights that sum to one. A sub-score is in [0, 1]. The task score is the weighted sum:

task_score = Σ (weight_i × sub_score_i)

A task passes when its score is at least the declared threshold. Thresholds are public on the task page. They are not uniform: tasks whose reference solution is intentionally hard to separate from a naive baseline use a lower bar, stated in the task manifest.

3. From task scores to a section and overall score

A section score is the arithmetic mean of its task scores. The overall score is the macro-average of section scores:

section_s = mean(task_scores in s)
overall   = mean(section_scores)

The macro-average gives every section equal weight, so a section with many tasks cannot dominate. Sections with no implemented tasks are omitted, not imputed. A model is ranked only when it covers every task in the edition; partial runs are listed separately.

The Go exporter recomputes these values from the published task rows and fails if they differ from the harness's own suite.json by more than 1e-9. The computation is small but duplicated on purpose: the site cannot drift from the harness silently.

4. Calibration baselines

Every task has four reference solvers:

Reference solvers shown on task pages.
SolverWhat it isWhy it is shown
NullValid but uninformative output.The floor: a schema-valid answer with no signal.
NaiveA plausible default analysis without the domain correction the task tests.What a competent but uncritical pipeline gets.
Reference solutionThe reference implementation shipped with the task.A realistic strong baseline, not a ceiling.
OracleTruth-aware calibration run.The achievable ceiling. Never mounted for a solve.

Baselines are context, not ranked models. A model score below the naive baseline means the attempted correction made things worse.

5. Timeouts, errors and zeros

A timeout or harness error is labelled in the status column. Its row keeps any partial score the harness produced, and is zero when no valid output existed. The dashboard never rewrites a timeout into a clean zero, so a model that was cut off is distinguishable from one that answered and scored zero. This matters for interpretation: a model that is accurate but too slow is not the same as a model that is wrong.

6. Editions and comparability

An edition fixes the dataset, benchmark version, task set, time cap and protocol. Scores are comparable only inside one edition. A changed task, dataset or protocol creates a new edition, and the old edition remains archived with its original caveats. The dashboard never merges runs across protocols to increase coverage.

7. What is public, and what is not

Public: task titles and descriptions, scoring weights, pass thresholds, sub-scores, calibration baselines, timing, protocol and dataset provenance.

Not public: prompts, task inputs, grader code, truth tables, agent transcripts, work directories and diagnostics that contain truth-side counts. The exporter uses an explicit field allowlist and the public data is decoded with a closed schema. A leak scan runs over the generated site before deployment.

8. Limitations of this edition

  • This edition is Exploratory: 26 tasks are planned and 20 minutes were allowed per task.
  • The model and the agent harness are confounded. A different harness may change a model's score.
  • There is one seed per task in this edition. Replicate variance is not yet estimated, so small differences should not be over-read.
  • Timing comes from artifacts and, for model wall-clock, from timestamps. It is indicative, not a controlled latency benchmark.
  • The generator is synthetic. Absolute performance on real data may differ, and tasks emphasize method choice and statistical honesty rather than large-scale engineering.

9. Reproducibility

Each edition publishes the dataset id, release checksum, generator commit, harness commit, dirty-tree flag, time cap, concurrency, seed count and backend on its edition page. The dashboard itself is a deterministic build: the same public data produces byte-identical HTML. The public data files are downloadable from the data page.

10. Citation

Not going to lie, why would you want to cite this? I guess if you want to cite this, you can name the edition, e.g., GeneBencher, First pilot (pilot-2026-11-07), 2026-11-07. Include the dataset id and release checksum when the claim depends on the data.
